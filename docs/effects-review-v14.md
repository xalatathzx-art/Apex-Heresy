# Проверка эффектов и их связи с листами и компендиумами

Проверена текущая рабочая копия Apex Heresy 1.3.4, включая уже внесённые в этой задаче изменения. Контракт ядра сверялся с установленными исходниками Foundry 14.365. Игровые документы не изменялись. Воспроизведения выполнены через реальные методы системы в Node VM с подменой внешних документов; повторный интерактивный прогон в мире для этого аудита не проводился.

## Вывод

Документы и редактор эффектов используют Foundry. Проблема — неполная и местами неверная интеграция с листами, состояниями и подготовкой контента. Active/passive/temporary в интерфейсе не являются тремя разными механизмами способностей: это группировка одного типа документа по disabled и наличию срока. Переписывать движок ActiveEffect не требуется; исправлять интеграцию нужно до расширения автоматизации способностей.

## Подтверждённые дефекты

### 1. Список не отражает фактическое применение

`DarkHeresySheet.organizeEffects` объединяет actor.effects со всеми item.effects. Не проверяет transfer, target, modifiesActor, active или isSuppressed. В штатном Actor.allApplicableEffects эффекты предметов включаются только с transfer=true.

Категории определяются только disabled и isTemporary. Воспроизведение: временный effect с active=false, isSuppressed=true, duration.expired=true, disabled=false попал в effects.active; effect предмета с transfer=false попал в effects.passive. Это неверное представление состояния, а не доказательство неправильного расчёта самим ядром.

Шаблоны персонажа и предмета показывают переключатель исключительно по disabled. Нет указания подавления, истечения, фактической цели, оставшегося времени или причины неприменения. Выключение disabled не возобновляет истёкший duration.expired.

### 2. Действия по строке могут выбирать чужой эффект

`DarkHeresySheet._getDocument` отдаёт приоритет короткому id. Если он есть, uuid вообще не сравнивается. Сначала перебираются эффекты Actor, затем эффекты Items.

Воспроизведение: строка с UUID Actor.a.Item.second.ActiveEffect.same разрешилась в Actor.a.Item.first.ActiveEffect.same. Локальные ID вложенных документов не обязаны быть уникальны между родителями. Ошибка затрагивает редактирование и переключение; запрет удаления Item-эффектов в разметке её не устраняет.

### 3. Снятие состояния может удалить источник в предмете

`hasCondition` возвращает активные эффекты из allApplicableEffects, в том числе Item. `removeCondition` затем вызывает existing.delete для minor либо existing.update для major, не проверяя родителя.

Воспроизведение: снятие stunned вызвало delete на эффекте с parent.documentName=Item. Значит, пользователь может удалить механическую часть предмета через кнопку состояния, хотя в таблице эффектов удаление такого источника специально закрыто замком. Нужно отдельно определить снятие собственного состояния, подавление вклада предмета и редактирование источника.

Эта несовместимость важна и для уже внесённых нами изменений: расширение корректного поиска состояний на эффекты предметов требует согласованного изменения пути удаления. Предыдущие проверки этого случая не покрывали.

### 4. Контент и сборщик не переносят готовые эффекты

Подсчитаны JSON-массивы в packs-src:

| Тип | Записей | С непустыми effects | С system.scripts |
|---|---:|---:|---:|
| talent | 417 | 0 | 0 |
| trait | 121 | 0 | 0 |
| specialAbility | 96 | 0 | 0 |
| psychicPower | 131 | 0 | 0 |

Это анализ исходников контента, не снимок всех установленных или пользовательских компендиумов. Отсутствие effects не исключает автоматизацию через встроенную логику системы.

`tools/build-items.mjs` при создании документа явно задаёт effects:[] и flags:{}. Поэтому простое добавление эффектов в входной JSON не обеспечит их попадание в компендиум, собранный этим инструментом.

V14 поддерживает самостоятельный тип компендиума ActiveEffect. В system.json системы зарегистрированы Item и RollTable packs; готовый системный pack эффектов не поставляется. При этом штатный ActorSheet поддерживает drop ActiveEffect и перенос Item вместе с данными: неверно утверждать, что импорт эффектов принципиально невозможен.

## Что уже штатное и не требует переписывания

- Создание, редактирование, обновление и удаление проходят через Foundry Documents. effect.sheet открывает штатный редактор ActiveEffectConfig; отдельного редактора ActiveEffect система не регистрирует.
- У ядра V14 есть system.changes, типы изменений, фазы и приоритеты, длительность и события истечения. Недавние изменения системы уже вернули расчёт к штатным фазам и registry.
- Старое создание temporary через duration.rounds использует совместимость V14: ядро переводит это в duration.value/units. Это устаревшая запись, но сама по себе не доказанный отказ таймера.
- Actor и Item sheets по-прежнему наследуют foundry.appv1.sheets. Новые CSS и DialogV2 не означают перенос самих листов на ActorSheetV2/ItemSheetV2. И наоборот, AppV1 не запрещает работу с современными документами эффектов.

## Другие ограничения интерфейса

- Система записывает большой ручной каталог CONFIG.ActiveEffect.attributeKeys, но в проверенном штатном ActiveEffectConfig нет его потребителя. Наличие этого объекта не доказывает работающий выбор полей в редакторе.
- Название источника у собственных Actor-эффектов берётся через effect.source?.name с запасным Actor, вместо штатного sourceName/origin. Связь с происхождением показывается неполно.
- Правила подавления оборудования пока покрывают weapon, armour, forceField и необязательный флаг activation=equipped. Выбор этой политики не представлен в общем редакторе эффекта системы. Эффекты иных типов оборудования требуют отдельного решения.
- Вкладка Scripts содержит текстовое поле. Исполнитель system.scripts в проверенном коде системы не обнаружен; внешние модули отдельно не проверялись.

## Порядок исправлений

1. Исправить разрешение UUID и защитить источники Item при снятии состояния.
2. Создать единое представление эффекта для обоих листов: источник, цель, действительно применяется ли, причина подавления, срок. Разделить «выключен», «истёк» и «подавлен».
3. Разделить действия «переключить», «возобновить срок» и «изменить источник». Не выдавать временность за активируемую способность.
4. Подключить выбор полей к реальным моделям данных и фазам V14; дать понятные подписи и политику применения оборудования.
5. Исправить сборщик: сохранять и проверять effects и нужные flags, проверять round-trip предмет → pack → Actor, повторное добавление одинаковых предметов и сроки импортированных эффектов.
6. Подготовить небольшой pack проверенных эффектов. Только затем наращивать автоматизацию способностей и переносить экраны эффектов в ApplicationV2.

Для приёмки нужны проверки включённых/выключенных/истёкших/подавленных эффектов, transfer true/false, двух предметов с одинаковыми вложенными ID, снятия состояния из Item, повторного пересчёта, окончания хода и импорта из компендиума. Одних тестов арифметики бонусов недостаточно.
